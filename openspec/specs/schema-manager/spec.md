# schema-manager Specification

## Purpose

Provides DDL schema design and manipulation tools to create and modify tables in SQLite, plus an interactive console for the direct execution of arbitrary SQL statements.

## Requirements

### Requirement: Visual table creation
The system SHALL provide a guided visual interface to define and create new tables with typed columns and integrity constraints.

#### Scenario: Successful creation of a new table
- **WHEN** the user specifies a valid table name, adds column definitions (name, SQLite type, PRIMARY KEY, NOT NULL, AUTOINCREMENT), and confirms creation
- **THEN** the system executes the corresponding `CREATE TABLE` DDL statement, adds the table to the active catalog, and shows it in the table list

#### Scenario: Validation of a duplicate or reserved table name
- **WHEN** the user attempts to create a table whose name already exists in the database
- **THEN** the system rejects the operation before execution and flags the name collision

### Requirement: Modifying and dropping tables
The system SHALL allow altering existing tables to add columns, renaming tables, or dropping entire tables after confirmation.

#### Scenario: Adding a column to an existing table
- **WHEN** the user specifies the name and type of a new column for an existing table
- **THEN** the system runs the `ALTER TABLE ADD COLUMN` statement and updates the table's schema view

#### Scenario: Renaming a table
- **WHEN** the user picks "Rename table" from the table's actions menu and provides a new, unused name
- **THEN** the system runs `ALTER TABLE ... RENAME TO ...`, keeps the table's data and schema intact, and updates the table list (following the renamed table if it was selected)

#### Scenario: Rejecting a rename that collides with an existing name
- **WHEN** the user tries to rename a table to a name already used by another table or view
- **THEN** the system rejects the operation and reports the name collision

#### Scenario: Dropping a table (DROP TABLE)
- **WHEN** the user requests to drop a table and explicitly confirms the destructive action
- **THEN** the system executes the `DROP TABLE`, removes the entity from the database, and refreshes the table list

### Requirement: Schema inspection
The system SHALL present the schema details of any selected table, showing its columns, data types, constraints, and associated indexes.

#### Scenario: Viewing the structural detail of a table
- **WHEN** the user opens the structure tab of a table
- **THEN** the system shows the list of columns with their name, affinity type, whether they are a primary key, whether they allow nulls, the default value, and the original `CREATE TABLE` statement generated by SQLite

### Requirement: SQL execution console
The system SHALL provide an interactive query editor to run any SQL statement against the open database.

#### Scenario: Running a selection query (SELECT)
- **WHEN** the user writes a `SELECT` query and presses "Run"
- **THEN** the system processes the query and shows an interactive table with the obtained results and the response time

#### Scenario: Running direct DDL or DML statements
- **WHEN** the user runs statements such as `INSERT`, `UPDATE`, `CREATE INDEX`, or `DELETE`
- **THEN** the system executes the statements, applies the changes, and reports the number of affected rows

#### Scenario: Terminal-style dark console
- **WHEN** the user opens the SQL Console tab
- **THEN** the system renders the editor with a dark terminal look (window title bar with the connected database name, `sqlite>` prompt, SQL syntax highlighting, and `Ctrl`/`Cmd` + `Enter` to run), with the messages and result grid styled in the same dark theme
- **AND** all editor assets are served locally from the vendored CodeMirror files, so the console keeps working offline

#### Scenario: Handling syntax or SQL execution errors
- **WHEN** a statement contains syntax errors or violates integrity constraints
- **THEN** the system catches the SQLite exception and shows the exact error message without interrupting the session

### Requirement: Dropping collections from the table list
The system SHALL allow dropping a table or view directly from the left table list, acting on the specific list item chosen regardless of which table is currently selected.

#### Scenario: Dropping the selected table from the list
- **WHEN** the user opens the actions menu of the currently selected table, chooses the drop action, and confirms the warning
- **THEN** the system executes `DROP TABLE`, removes the table, refreshes the table list, and clears the workspace because the active table was dropped

#### Scenario: Dropping a table that is not selected
- **WHEN** the user drops a table from the list while a different table is selected
- **THEN** the system drops the chosen table, refreshes the list, and keeps the currently selected table and its workspace unchanged

#### Scenario: Dropping a view from the list
- **WHEN** the user drops a view from the list and confirms the warning
- **THEN** the system executes `DROP VIEW`, removes the view from the list, and leaves the underlying tables and their data intact

#### Scenario: Cancelling the drop
- **WHEN** the user dismisses the confirmation without confirming
- **THEN** the system performs no drop and leaves the schema and list unchanged

#### Scenario: Drop rejected by the database
- **WHEN** the database refuses the drop (for example, a foreign-key dependency)
- **THEN** the system reports the SQLite error to the user and the session continues

### Requirement: Drop warning distinguishes tables from views
The system SHALL require an explicit confirmation before dropping, presenting a warning whose text reflects the kind of entity being dropped.

#### Scenario: Warning for a table drop
- **WHEN** the user initiates dropping a table
- **THEN** the confirmation warns that all of the table's data will be destroyed

#### Scenario: Warning for a view drop
- **WHEN** the user initiates dropping a view
- **THEN** the confirmation warns that only the view definition will be removed and underlying data is not affected
